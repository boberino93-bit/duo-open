EXECUTIVE FINDING
=================

Current main tears down Duo's terminal cover frame as soon as native-cover topology becomes
logically authoritative near <=12°. That has no destination presentation barrier.

However, the obvious fix — wait for Duo Open's existing SurfaceControl transaction-completed /
present-fence callback — is NOT an exact proof that Samsung's native cover content behind the Duo
overlay has presented. Android's contract is transaction-scoped: a completed listener proves the
transaction to which it was attached was presented. Display.getState is only a display power/state
fact, and View frame-commit is only swap-chain submission.

Therefore the terminal handoff needs an explicit evidence taxonomy and a bounded fallback. The
production owner should not turn a valid Duo-owned present callback into a false native-content
acknowledgement.

SOURCE-CONFIRMED CURRENT FAILURE WINDOW
=======================================

At the native-cover threshold:
  Fold7ContinuityController
    COVER_VISUAL -> NATIVE_COVER
    emits HideMirror + ReleaseSecondary

  Fold7ContinuityCoordinator
    HideMirror -> mirrorHost.detach() immediately
    ReleaseSecondary -> hide again + async privileged lease release

There is no current state for "native route observed, terminal Duo frame intentionally retained
until landing is safe".

EVIDENCE TAXONOMY
=================

Use four non-interchangeable classes:

  1. ROUTE_OBSERVED
     Facts such as coverActive, coverIsDefault, !innerActive, display state ON, routeReady.
     Meaning: the OS/Samsung route is logically/power ready.
     NOT proof that the destination app frame is visible.

  2. VIEW_FRAME_COMMIT
     registerFrameCommitCallback for Duo's frozen overlay.
     Meaning: Duo content was rendered/submitted to the swap chain.
     Android explicitly says it may not yet be visible.

  3. DUO_TRANSACTION_PRESENTED
     addTransactionCompletedListener / present fence on a Duo-created SurfaceControl.Transaction.
     Meaning: the frame containing THAT transaction's updates was presented.
     Strong exact evidence for Duo's own transaction, but still not proof of another process's
     native cover content behind the overlay.

  4. NATIVE_CONTENT_PRESENTED
     Exact evidence specifically tied to the Samsung/native destination content intended to
     replace the Duo overlay.
     Current public app path does not expose such an acknowledgement.

Only class 4 is safe as an unconditional EARLY terminal release trigger. Classes 1-3 remain useful
for telemetry and staging but must not be promoted into class 4 by naming alone.

RECOMMENDED GEN3 SHAPE: TERMINAL HANDOFF GUARD
==============================================

When current semantic ownership decides COVER_VISUAL -> NATIVE_COVER:

A) Begin an exact terminal handoff owner rather than detaching immediately.
   Identity should compose the service-stable/current Gen3 identities already being introduced:
     serviceEpoch + closeCycleId + visualAttemptId/handoffSequence (+ hostLeaseId below owner).
   Do not key it to a disposable Display id or a host-local sequence that can reset on remap.

B) Freeze the current terminal Duo cover image in place.
   - Stop source churn / stop attempting to advance the visual.
   - Do not detach the overlay yet.
   - Native topology may continue changing behind it.

C) Record evidence without conflating it.
   - native route observed
   - Duo frame commit
   - Duo transaction presented / present-fence time
   - exact native-content presented, if an OEM/privileged source is later proven

D) Release on FIRST of:
   1. exact NATIVE_CONTENT_PRESENTED for the same immutable handoff owner; OR
   2. bounded refresh-relative deadline; OR
   3. explicit semantic cancellation (opening reversal, service stop, privilege/authority loss,
      service-epoch rollover), according to primary ownership policy.

E) Reject stale callbacks.
   Any callback from an older service/cycle/visual/handoff owner is telemetry only and cannot
   release the current terminal frame.

WHY BOUNDED FALLBACK IS REQUIRED
================================

With no exact public cross-process native presentation acknowledgement, an unbounded wait would
replace a possible flash with a frozen overlay hang. The guard must terminate even when all
presentation callbacks are absent, stale, or uncorrelated.

Use a REFRESH-RELATIVE experimental parameter rather than a magic millisecond constant:

  deadline = nativeRouteObservedNs + graceFrames * ceil(1e9 / observedCoverRefreshHz)

Candidate device sweep (NOT production-proven):

             1 frame     2 frames     3 frames
  60 Hz      16.667 ms   33.333 ms    50.000 ms
  90 Hz      11.111 ms   22.222 ms    33.333 ms
  120 Hz      8.333 ms   16.667 ms    25.000 ms

Start physical testing at 2 frames; sweep 1/2/3. Cap the experiment at 3 frames unless physical
Fold7 evidence justifies otherwise. The 2-frame starting point is a design hypothesis, not a
measured recommendation: it gives one complete subsequent compositor opportunity even when route
observation occurs just after a vsync, while keeping the worst planned hold small.

Implementation should keep an absolute monotonic deadline even if release is normally scheduled on
a cover-display frame/vsync callback, because frame callbacks can themselves stop during topology
churn.

IMPORTANT NON-FIX
=================

Do NOT implement:

  if (duoTransactionCompleted) detachOverlay()

and call it "native landing presented".

Counterexample allowed by the API contracts:
  t=0 ms   native route/default fact becomes true
  t=4 ms   Duo-owned transaction-completed callback fires
  t=20 ms  Samsung/native application content reaches the panel

The Duo callback is valid in this sequence, yet releasing at 4 ms still creates a 16 ms uncovered
window. The model preserves this counterexample deliberately. It is a logical/API-scope proof, not
a claim that Fold7's measured delays equal those numbers.

MODEL VALIDATION
================

Focused tests: 8/8 PASS
  - proxy evidence cannot release
  - exact native evidence releases
  - 120 Hz two-frame deadline bounded
  - 60 Hz deadline scales with refresh
  - stale prior owner rejected
  - current owner cancellation explicit
  - proxy-release counterexample remains possible
  - 1/2/3-frame sweep matrix stable

Adversarial model:
  100,000 fixed-seed randomized event sequences PASS
  seed: 0xD00F7

Randomized events include topology-route evidence, View commit, Duo transaction present, exact
native evidence, stale exact evidence, timeout ticks, owner replacement, and cancellation. Core
invariants:
  - ROUTE_OBSERVED / VIEW_FRAME_COMMIT / DUO_TRANSACTION_PRESENTED never release by themselves.
  - stale prior-owner evidence cannot release a replacement owner.
  - terminal hold is bounded by the configured deadline when ticked.
  - only exact-native, bounded deadline, or explicit cancellation produces release.

INTEGRATION GUIDANCE FOR PRIMARY
================================

1. Do not put the delay directly into Fold7ContinuityController as a blind sleep.
   Let the controller emit semantic native-cover handoff demand; keep timing/evidence policy in an
   exact owner/guard adjacent to the Gen3 visual/presentation owner.

2. Preserve current semantic threshold logic unless device evidence says otherwise.
   This R&D is about release timing after route observation, not moving the <=12° threshold.

3. On route observation, keep the last accepted visual immutable and stop mutation.
   A grace interval with a changing overlay defeats the purpose and complicates correlation.

4. Use service-stable presentation/handoff identity from the concurrent reviewer/state work.
   Current DisplayMirrorHost-local Fold7PresentationLease identities are not sufficient as a
   cross-host owner key.

5. TransitionLab already contains most required timing fields. Add only sparse terminal-handoff
   events if needed, e.g.:
     terminal-handoff-begin
     terminal-handoff-evidence (reason=evidence class)
     terminal-handoff-release (reason=exact-native|deadline|cancel)
   Carry the same service/cycle/visual identity and actual observed refresh rate.

6. Do not block on SyncFence.wait(). Existing SurfaceTransactionProbe's nonblocking pattern is the
   right one. The handoff guard is a logical lease with callbacks + monotonic timeout.

PHYSICAL FOLD7 VALIDATION PLAN
==============================

Device validation is mandatory before selecting graceFrames.

Run close cycles at each candidate graceFrames = 0, 1, 2, 3, with current production/Gen3 logging:
  - slow manual close
  - normal close
  - fast close
  - stop/hover around 12°
  - reverse open just before/after native-route observation
  - logical display remap during terminal phase if reproducible
  - Shizuku/authority loss during terminal phase
  - 60 Hz and adaptive/high-refresh configurations where available

For each cycle record:
  routeObservedNs
  cover refresh rate at admission
  terminalGuardBeginNs
  Duo frame-commit timestamp (proxy)
  Duo transaction completed / present-fence timestamp (proxy)
  exact-native timestamp if a valid OEM/privileged source is discovered
  detach/release request timestamp
  release completion timestamp
  outcome: clean / flash-gap / frozen-hold-too-long / reversal regression

Use high-frame-rate external video as the ground-truth visual outcome during the sweep. Pick the
smallest graceFrames that eliminates observed discontinuity without a perceptible frozen tail.
Do not infer the winning value from this pure model.

BOTTOM LINE
===========

The architectural risk is real, but the release condition must not overclaim evidence. Current
main releases too early; a Duo-owned presentation callback alone can still release too early. The
safe Gen3 contract is: exact owner + frozen terminal frame + exact-native evidence when genuinely
available + bounded refresh-relative fallback + stale callback fencing + device calibration.

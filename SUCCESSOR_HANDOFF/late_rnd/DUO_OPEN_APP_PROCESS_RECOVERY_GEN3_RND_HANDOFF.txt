EXECUTIVE RESULT
----------------
A source-confirmed app-process recovery gap remains even after reconciling the
staged Gen3 Phase1 V2 CAS design.

Duo's Shizuku UserService is configured daemon(true). Shizuku documents daemon
UserService mode as continuing after the app process dies until explicitly
unbound. Therefore the privileged DuoShellService process and its in-memory
Fold7CoverPanelLease can outlive the app/accessibility process.

A fresh app process creates a new FoldOverlayService serviceEpoch and a fresh
Fold7Gen2Kernel, but its startup sequence can query and accept a surviving
non-IDLE daemon-side cover lease before continuity.arm(). On current main the
lease token has no app serviceEpoch. Primary Phase1 V2 correctly adds
ownerServiceEpoch/ownerCloseCycleId and prevents a prior-process lease from
being treated as the new close cycle without exact CAS. However, Phase1 V2 does
not change the startup recovery flow: a foreign HELD lease may remain resident
while the fresh process enables renderOwnershipArmed and has no local active
close cycle.

The recommended Gen3 addition is a small service-start recovery gate that runs
before normal render ownership is armed. It classifies a non-IDLE token owned
by another serviceEpoch as FOREIGN_PRIOR_SERVICE, cleans/reconciles it exactly,
and only then permits stable-rest startup. If restart occurs mid-transition,
the new process should not reconstruct/join the dead process's semantic attempt
from one instantaneous angle/topology sample; after cleanup it should wait for
a fresh semantic movement/edge before creating new continuity authority.

This composes with, rather than replaces:
- primary Phase1 V2/V4 exact-CAS cover authority,
- reviewer Shizuku daemon-restart UNKNOWN_RECOVERY work,
- state-rd exact close-cycle prime ownership,
- state-rd opening-attempt ownership,
- reviewer presentation ownership,
- display-rd terminal handoff/readiness,
- state-rd angle-authority/failover work.

CURRENT IMPLEMENTATION RECONSTRUCTION
-------------------------------------
1. App and accessibility service lifetime

DuoApplication.onCreate():
- initializes diagnostics/settings/OverlayFeature;
- logs the previous process exit using ActivityManager historical exit reasons;
- OverlayFeature.initProcess() initializes ShizukuBridge once per app process.

FoldOverlayService:
- AccessibilityService in the normal app process;
- serviceEpoch = SystemClock.elapsedRealtimeNanos() at service instance creation;
- creates a fresh Fold7Gen2Kernel(serviceEpoch);
- all close-cycle/frame/readiness owners are in-memory and therefore lost when
  the app process dies.

PersistentRuntimeService:
- a foreground service in the same app process (no android:process override);
- returns START_STICKY;
- therefore Android may recreate it after the app process is killed.

FoldOverlayService.onServiceConnected() startup order relevant to this finding:
- ensure foreground runtime;
- construct Fold7ContinuityCoordinator with the fresh Gen2 kernel;
- start hinge + DeviceState + Shizuku integrations;
- collect ShizukuBridge.state;
- on Ready:
    continuity.onPrivilegedReady();
    if first ready for this accessibility-service lifetime: continuity.arm();
    primeCoverRoute();
- syncDisplays().

2. Daemon-side lifetime

ShizukuBridge.UserServiceArgs:
- .daemon(true)
- .processNameSuffix("shell")

Shizuku documents daemon UserService mode as independent of the app process:
non-daemon stops when app process dies; daemon continues until unbind.

DuoShellService therefore has a distinct lifetime and owns:
- shellSession = elapsedRealtimeNanos();
- Fold7CoverPanelLease instance;
- serialized cover mutation executor;
- mirror lease/session state.

An abrupt app-process death does not imply DuoShellService was destroyed.

3. Current main first reconcile

Fold7ContinuityCoordinator.onPrivilegedReady():
- coverAuthority.onConnectionEpoch(ShizukuBridge.connectionEpoch)
- ensureMirrorSession("shizuku-ready")
- reconcileCoverLease("shizuku-ready")

A fresh app-side Fold7CoverLeaseSnapshotGate has no accepted snapshot, so
reconcileCoverLease sends shellSession=0.

DuoShellService COVER_PANEL_LEASE_V3 reconcile treats requestShellSession=0 as
a wildcard:
- only a nonzero mismatching session is rejected;
- otherwise reconcileCoverLeaseV2() runs and current shell snapshot is returned.

Fold7CoverPanelLease.onTopology() only reconciles RELEASE_PENDING and
UNKNOWN_RECOVERY. HELD is deliberately left HELD.

The app acceptance gate accepts the first valid shell session/revision and a
non-IDLE token. On current main the token contains:
- shellSession
- leaseId
- leaseEpoch
- ownerGeneration
- physicalDisplayId
but no app serviceEpoch / closeCycleId.

Thus current main cannot distinguish "HELD by my fresh service instance" from
"HELD by the dead app process" at the app token boundary.

4. arm() does not clean a foreign cover lease

continuity.arm():
- gen2.cancelActiveCycle()      // fresh process has none
- renderOwnershipArmed = true
- ensureMirrorSession("arm")
- controller.reset(one current angle or inferred rest angle, topology)
- hideMirror(... stopShellMirror=true)

The explicit source comment says arm clears a stale mirror but does not issue a
power command. hideMirror is mirror cleanup; it is not Fold7CoverPanelLease
release. Therefore a daemon-side HELD cover lease can remain resident through
fresh-process arm.

Later topology reconcile still does nothing to a HELD lease.

5. Controller bootstrap is intentionally non-provenance-preserving

Fold7ContinuityController.reset():
- assigns state from one instantaneous angle/topology snapshot;
- does not emit a normal transition callback;
- therefore does not begin a new Fold7CycleEnvelope close cycle.

This is good in one respect: a fresh process does not automatically invent a
new close cycle from a mid-fold sample. But it also means there is no explicit
RECOVERING state that blocks normal render authority while surviving privileged
state is reconciled.

DOMINANT LIMITATION
-------------------
There is no explicit app-process startup recovery barrier between:

  "fresh process has connected to a daemon that may still carry prior-process
   privileged cover state"

and

  "normal continuity render ownership is armed."

Source-confirmed failure sequence:

A. Old app serviceEpoch E1 is in a close cycle; shell cover lease is HELD.
B. Android app process dies abruptly. FoldOverlayService.onDestroy is not
   guaranteed to run on process kill, so its graceful release path may not run.
C. daemon(true) DuoShellService survives with the HELD lease / shellSession.
D. Android recreates/rebinds app components; new FoldOverlayService has E2 and
   no active local close cycle.
E. Shizuku Ready arrives. onPrivilegedReady() starts reconcile before arm.
F. Fresh app sends shellSession=0 wildcard; daemon returns HELD lease from E1.
G. Current main accepts it without E1/E2 distinction. Phase1 V2 accepts the
   structurally valid token while preserving ownerServiceEpoch=E1.
H. arm() enables renderOwnershipArmed, cancels no local cycle, resets policy
   from instantaneous posture, hides mirror, but does not release cover lease.
I. Foreign HELD authority can remain resident after startup. In Phase1 V2 it is
   correctly not the owner of a new close cycle without V4 CAS, but it is still
   not resolved before normal startup completes.

Why this matters architecturally:
- privileged state outlives semantic/content/presentation provenance;
- a new process should not silently inherit an unfinished physical attempt;
- stable-open startup should not carry an old secondary cover hold indefinitely;
- mid-transition startup cannot reconstruct the exact dead-process frame,
  presentation attempt, opening attempt, or movement identity from one sample.

PROPOSED GEN3 RECOVERY OWNER
----------------------------
Suggested pure owner: Fold7ProcessRecoveryGate (name flexible).

Phases:
  RECOVERING
  WAIT_FRESH_EDGE
  READY

Inputs:
- current app serviceEpoch Enew;
- Shizuku connection epoch + exact shell snapshot;
- accepted Phase1 V2 token including ownerServiceEpoch/ownerCloseCycleId;
- current physical posture/topology;
- angle-authority freshness when available;
- cleanup completion / shell state.

Rule 1 — startup starts fail-closed
----------------------------------
On a fresh FoldOverlayService instance:
- renderOwnershipArmed must remain false until recovery gate reaches READY;
- no new close/open visual attempt is created from startup snapshot alone.

Rule 2 — classify first shell snapshot
--------------------------------------
IDLE:
- no foreign privileged mutation is resident;
- continue posture bootstrap.

NON-IDLE, ownerServiceEpoch == Enew:
- may only occur for an already-initialized same service instance/re-entry;
- keep normal exact-owner checks.

NON-IDLE, ownerServiceEpoch != Enew:
- FOREIGN_PRIOR_SERVICE.
- Do not claim it as the current semantic attempt.
- Do not allow it to satisfy current readiness/presentation/content ownership.
- initiate exact cleanup/reconcile.

Legacy/non-IDLE snapshot with no valid service epoch:
- treat as foreign/unknown, never as current.

Rule 3 — exact cleanup
----------------------
If a valid exact old token is available, use exact release semantics for that
actual token; do not issue raw physical OFF.

Phase1 V2 already makes token identity stronger. A minimal implementation can
reuse the accepted old token for exact release, then keep RECOVERING until a
new accepted shell snapshot proves IDLE (or an explicitly designed native-safe
terminal state has cleared shell ownership).

If daemon itself restarted / UNKNOWN_RECOVERY applies:
- delegate to the existing reviewer Shizuku-recovery design;
- do not create a second conflicting recovery state machine.

Cleanup must be idempotent because the app may die again during cleanup.

Rule 4 — bootstrap posture only after privileged cleanup
--------------------------------------------------------
Stable OPEN_INNER:
- arm after shell is clean.

Stable NATIVE_COVER:
- arm after shell is clean/native-safe.

MID_TRANSITION / ambiguous posture:
- prior semantic provenance is gone;
- do not join old close/open attempt;
- enter WAIT_FRESH_EDGE and let Samsung native behavior own the immediate state;
- require a fresh movement/semantic edge under the new process before starting
  a new cycle/visual attempt.

This is intentionally conservative. The new process cannot reproduce the exact
old frozen frame/presentation/opening attempt after process death, so pretending
continuity is intact would be false provenance.

Rule 5 — compose with AngleAuthority
------------------------------------
The separate state-rd angle-authority work found stale/failover hazards.
Therefore recovery should not decide "stable vs mid-transition" from an
unqualified stale precise sample. Prefer:
- physical topology endpoint authority where unambiguous;
- otherwise a fresh AngleAuthority sample/edge once that owner lands;
- otherwise WAIT_FRESH_EDGE.

Do not introduce synthetic visual geometry just to exit recovery.

MINIMAL INTEGRATION SHAPE
-------------------------
Conceptually:

onServiceConnected:
  recovery = Fold7ProcessRecoveryGate(serviceEpoch)
  continuity.startDisarmedForRecovery()

on Shizuku Ready:
  snapshot = reconcile/status
  recovery.observe(snapshot, topology, freshAngleEvidence)
  if recovery.action == RELEASE_FOREIGN(token):
      exactRelease(token)
      remain disarmed
  if recovery.state == READY:
      continuity.armRecovered(...)
  if recovery.state == WAIT_FRESH_EDGE:
      remain disarmed for visual/secondary ownership

on exact release/status result:
  recovery.observe(...)

on fresh semantic edge:
  if recovery == WAIT_FRESH_EDGE and privileged state clean:
      recovery -> READY
      begin only a NEW serviceEpoch-scoped attempt

Do not move this into PanelEngine. Process recovery is service/authority scope.

   process without intentionally unbinding/stopping the daemon UserService.
   Observe whether shell PID/session and lease survive.

3. If shell survives:
   Current/Phase1 expected reconstruction: first reconcile sees prior HELD.
   Recovery-gate expected: classify foreign, release/reconcile exactly, stay
   disarmed until shell clean, then arm only from stable rest/fresh edge.

4. Repeat while process termination occurs during opening / partial fold.
   Expected Gen3 behavior: no resurrection of the old semantic attempt; after
   cleanup, wait for fresh edge if posture cannot be proven stable.

5. Kill daemon as well as app process.
   Expected: this falls into existing Shizuku daemon-restart recovery, not the
   surviving-daemon branch from this workstream.

6. Re-kill app during recovery cleanup.
   Expected: exact release/reconcile remains idempotent; next process again
   starts RECOVERING and does not arm early.

PASS invariants:
- no foreign prior-service non-IDLE lease counts as current cycle authority;
- normal render ownership is not armed while foreign cleanup is unresolved;
- no raw physical OFF;
- no stale old-process visual/frame/presentation attempt is resurrected;
- stable rest recovers automatically after exact cleanup;
- ambiguous mid-transition requires fresh new-process semantic evidence;
- Shizuku daemon-restart path remains compatible.

RISKS / TRADEOFFS
-----------------
1. Conservative visible degradation after a mid-transition process restart.
   Accepted: provenance is gone; a short native Samsung handoff is safer than
   inventing stale continuity.

2. Cleanup can add startup latency.
   Bound it, keep asynchronous, expose diagnostics, but do not arm ahead of
   unresolved foreign privileged state.

3. Prior HELD lease may still be physically safe/usable.
   Phase1 V4 can exact-CAS transfer it on a future fresh close cycle. That is
   different from silently inheriting it at startup. Keep transfer explicit.

4. Repeated process death during cleanup.
   Exact tokens/revisions and fail-closed startup make this naturally retryable.

5. Deployment compatibility.
   Phase1 V2 is staged, not current main. Recovery integration should target the
   post-Phase1 ownerServiceEpoch token shape rather than reimplementing it.

PRIMARY INTEGRATION RECOMMENDATION
----------------------------------
After Phase1 V4 authority lands, add the process-start recovery gate before
Phase2 visual/compositor ownership is allowed to arm. The clean architectural
contract is:

  serviceEpoch establishes app-process semantic authority;
  shell lease identity establishes privileged mutation authority;
  startup recovery proves the two lifetimes are reconciled;
  only then may content/visual/presentation owners become live.

The key acceptance criterion is not "did startup produce a plausible state?"
It is "has every non-IDLE privileged state from another app serviceEpoch been
explicitly resolved before this process claims normal continuity authority?"

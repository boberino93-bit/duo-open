1. EXECUTIVE SUMMARY
==================================================

SUBSYSTEM
The terminal OPENING handoff from Duo's cover opening visual to Samsung/native inner composition.

NARROW QUESTION
When the phone is opening from fully closed, can CURRENT main end Duo's cover opening visual because the inner display is logically active and the hinge has reached the open latch, before there is stronger evidence that the native inner destination has produced usable current-cycle pixels?

ANSWER FROM SOURCE
Yes, the source has this architectural gap.

CURRENT main makes the terminal opening release from geometry/topology facts:
- Fold7ContinuityController transitions an opening state to OPEN_INNER when angle >= 172 degrees and topology.innerActive is true.
- Fold7ContinuityCoordinator defines innerActive from Display.state != STATE_OFF && != STATE_UNKNOWN.
- FoldOverlayService.reconcileContinuityCoverRendering() clears the semantic opening latch when the controller is no longer OPENING_FROM_CLOSED or INNER_HANDOFF.
- Fold7CoverRenderPolicy then stops the early opening visual.
- PanelEngine.endContinuityOpeningVisual() removes the cover overlay.

No current-cycle native-inner frame/capture/presentation evidence gates that terminal release.

There is unusually strong internal corroboration for the distinction between "display active" and "usable pixels": PanelEngine's existing afterSwap capture path explicitly says that a freshly switched-on panel may still be lighting up, retries black captures, and allows up to a 1.1 s capture timeout. In addition, the service ordering on hinge callbacks performs controller transition + cover-render reconciliation before calling PanelEngine.onHinge() on the engines. At the same 172-degree constant, inner PanelEngine.onHinge() latches inner-open and removes its own flat overlay. Thus both sides can relinquish bridge rendering at the open threshold before any explicit destination-content proof participates in the decision.

This is a CONFIRMED SOURCE ARCHITECTURE GAP, not a claim that a visible flash is proven on a physical Fold7. The physical incidence and severity require device traces/high-frame-rate video.

GEN2 DIRECTION
Do not create a competing top-level visual owner. Primary is already integrating one exact Gen3 visual-attempt owner. Add a terminal opening-release condition beneath that owner:

- controller OPEN_INNER = geometric/semantic intent to finish opening;
- inner destination readiness = separate evidence;
- release opening visual as PROVEN only after both are true for the same current opening attempt and route epoch;
- route loss, privilege/authority loss, manual stop, reversal, service rollover, and the existing bounded watchdog remain explicit degraded/cancel outcomes rather than being mislabeled as readiness success.

Use a stable identity aligned with the accepted opening visual attempt, plus destination-route identity:
serviceEpoch + openingCycle/movementId + visualAttemptSequence + innerRouteEpoch + readinessAttemptSequence.

Where possible, reuse the existing inner afterSwap capture path rather than adding a mandatory screenshot. AccessibilityService.ScreenshotResult.timestamp already provides exact uptime for when a screenshot was taken. Treat black/secure/uncapturable results explicitly as ambiguous/failure evidence; never synthesize "ready" from time alone.

MODEL RESULT
Corrected reduced model PASS=16/16 including a deterministic 100,000-operation fixed-seed adversarial stream.

NEGATIVE RESULT PRESERVED
The first proposed model FAILED its fuzz invariant because it left a completed opening handoff owner active after release, allowing later route-remap events to mutate evidence in a terminal attempt. Design was corrected: release is terminal/immutable for that opening attempt. The corrected model then passed all tests and fuzz.

4. ANDROID PLATFORM EVIDENCE
==================================================

OFFICIAL DOC 1
https://developer.android.com/reference/android/view/Display
- Display.STATE_ON: "The display is on."
- Display.getState(): returns state such as on/off/doze/etc.
This API is a display state/power state. It does not document "the native task's first frame has been presented" semantics.

OFFICIAL DOC 2
https://developer.android.com/reference/android/accessibilityservice/AccessibilityService.ScreenshotResult
- getTimestamp(): timestamp of taking the screenshot.
- timebase: milliseconds of non-sleep uptime since boot, SystemClock.uptimeMillis().
This provides an exact temporal observation that can be bound to an opening attempt/cycle.

OFFICIAL DOC 3
https://developer.android.com/reference/android/view/ViewTreeObserver#registerFrameCommitCallback(java.lang.Runnable)
- frame-commit callback means current rendering content has been rendered and submitted to the swap chain;
- docs explicitly say the frame may not yet be visible.
This is useful for Duo-owned View content but does not by itself prove native inner pixels are physically visible.

INTERPRETATION
No Android public API examined here turns Display.STATE_ON into native-content presentation proof. Runtime gating therefore needs a stronger observable than Display state if the goal is to avoid a source-level handoff gap. A screenshot/capture observation is one practical stronger signal already present in Duo, but physical-photon timing still requires device validation.

7. PROPOSED GEN2 TERMINAL HANDOFF CONTRACT
==================================================

DO NOT ADD A SECOND TOP-LEVEL VISUAL OWNER.
Reuse the exact visual attempt selected by primary / state-rd.

PROPOSED SUBORDINATE OWNER
OpeningTerminalHandoffState, attached to current exact opening visual attempt.

IDENTITY
- serviceEpoch
- openingCycleId or movementId (use primary's canonical naming)
- visualAttemptSequence
- innerRouteEpoch
- readinessAttemptSequence

STATE / FACTS
- semanticOpeningActive
- controllerWantsOpenInner
- coverVisualStillHostable
- currentInnerRouteIdentity
- innerDestinationEvidence
- terminalOutcome

TERMINAL OUTCOMES
1. PROVEN_INNER_READY
   - controller wants OPEN_INNER
   - current exact opening attempt is still current
   - current-route inner destination evidence is accepted
   - release opening visual

2. DEGRADED_COVER_ROUTE_LOST
   - cover host/route no longer exists or cannot carry the visual
   - release because retaining bridge is physically impossible
   - DO NOT record as readiness success

3. DEGRADED_WATCHDOG_NO_PROOF
   - existing bounded safety timeout expires before readiness proof
   - release to avoid a stuck cover visual
   - DO NOT record as readiness success

4. CANCEL_REVERSAL
   - opening reverses to closing
   - invalidate attempt/evidence

5. CANCEL_PRIVILEGE_OR_AUTHORITY_LOSS
   - exact visual authority revoked

6. CANCEL_SERVICE_EPOCH
   - service/process lifecycle changes

EVIDENCE ACCEPTANCE
A readiness event must match:
- current service epoch;
- current opening cycle/movement;
- current visual attempt;
- current inner route epoch;
- capture/observation time >= opening-cycle start;
- monotonically accepted readiness attempt sequence.

ROUTE REMAP
A remap increments innerRouteEpoch and invalidates prior route evidence. The semantic visual attempt may remain active/rebind according to state-rd's opening owner, but readiness must be re-proven for the replacement route.

REVERSAL
Opening evidence from attempt A cannot release a later opening attempt B. Reversal terminates A.

POST-RELEASE IMMUTABILITY
Once terminalOutcome is recorded and visual authority is released, later callbacks cannot mutate the completed attempt. This was the flaw caught by the first model run.

8. WHERE READINESS EVIDENCE CAN COME FROM
==================================================

PREFERRED LOW-INTRUSION START
Reuse the existing inner afterSwap capture path as an observation publisher rather than adding a new mandatory screenshot.

When PanelEngine receives a current inner capture result:
- publish opening destination evidence to the service-stable terminal owner if an opening attempt exists;
- include the current route epoch and exact screenshot timestamp when Accessibility screenshot is used;
- do not grant readiness from a capture request that began before the opening attempt/route epoch unless exact capture timestamp proves it belongs after the boundary.

BLACK CAPTURE
Current source intentionally retries black afterSwap captures because black can mean a panel is still waking.
Recommended evidence quality:
- CAPTURED_NONBLACK: strong runtime readiness evidence.
- CAPTURED_BLACK_AFTER_RETRIES: ambiguous, not equivalent to proven readiness; legitimate black content means this can false-negative.
- SECURE/FAILED: no readiness proof.

Do not solve ambiguity by inventing a new fixed wait and calling it success.
The existing watchdog can remain a degraded release escape hatch.

IMPORTANT LIMITATION
A screenshot/capture observation is not the same thing as a SurfaceFlinger present fence for the native app, and neither is literal photon proof. The objective is to eliminate the weaker source-level dependency on Display state alone, then measure the resulting relationship on the Fold7.

ALTERNATIVE / FUTURE EVIDENCE
If Gen3's dedicated visual/content backend gains a stronger native-inner readiness primitive, plug it into the same owner contract. The contract should not depend on PanelEngine as the permanent authority.

10. REGRESSION / FAILURE ANALYSIS
==================================================

LATENCY RISK
Waiting for evidence can extend cover visual lifetime relative to current 172-degree teardown. This is intentional only when the cover route is still usable. Measure it; do not guess.

VISUAL STICK RISK
If capture/readiness never arrives, a bridge could remain too long. Preserve an explicit bounded watchdog as a DEGRADED release, plus immediate route-loss release.

SECURE CONTENT
Screenshot can fail on secure content. Do not replay unrelated stale content and do not label timeout as ready. Degrade via route loss/watchdog/native behavior.

LEGITIMATELY BLACK CONTENT
A black-pixel heuristic is not semantic proof of not-ready. Treat black as ambiguous rather than permanent failure; do not make nonblack pixels a correctness requirement for all apps.

POWER
If existing afterSwap capture is reused, the core proposal adds no mandatory extra capture. Any additional probe should be separately measured and justified.

RACE / REMAP
Evidence must carry route epoch. A capture for route A cannot release a visual now bound to route B.

SERVICE RESTART
New serviceEpoch invalidates old evidence.

CONTROLLER GENERATION
Do not use controller.generation as the sole stable opening cycle identity; it changes across transitions. Reuse state-rd/primary stable opening attempt identity.

THRESHOLDS
Do not change 3/8/172/166 or other existing hinge thresholds to hide the problem. This is an ownership/evidence issue.

14. FINAL CONCLUSION
==================================================

CURRENT main has a real evidence-level asymmetry on opening: it wakes the inner early because route/pixel readiness can lag, but terminal completion still collapses to OPEN_INNER from 172-degree geometry plus Display-active topology. The renderer already contains black-capture retry logic acknowledging that a newly active panel can still be visually unready. The clean Gen3 fix is not another timeout or threshold tweak; it is to make terminal release an explicit outcome of the exact visual attempt and distinguish PROVEN native-inner readiness from DEGRADED forced release.

This contract is compatible with the primary's live Gen3 alpha architecture and the completed state-rd opening-owner workstream.

SUBSYSTEM

WHY THIS IS A DISTINCT TARGET
- display-rd owns fold-effect/compositor and exact CoverVisualLease/visual-intent design.
- performance-rd owns causal latency instrumentation/correlation.
- state-rd owns close-cycle prime/capture arbitration and current opening one-shot ownership work.

- This work does NOT redesign those subsystems. It defines the exact presentation authority beneath the visual owner and the rules by which visible ownership can be asserted or revoked.

STRONGEST SOURCE-CONFIRMED FINDING
CURRENT main exposes `visualMirrorActive` as:
  mirrorRequested && controller.state == COVER_VISUAL

`showMirror()` sets mirrorRequested=true before a mirror session, usable host, content bind, transaction submission, or physical-presentation callback exists. `syncMirrorHost()` can return because the mirror session is not open, topology is incomplete, source/destination IDs collide, host construction fails, attach fails, or later content binding fails. Therefore CURRENT can report the visual as active when no visual has been presented and, in some paths, when no usable host exists at all.

The mismatch is architectural, not merely diagnostic: `Fold7CoverRenderPolicy` gives privileged Gen2 blanket cover ownership, and `FoldOverlayService.syncDisplays()` suppresses ordinary engine evaluation while `visualMirrorActive` is true. Thus demand/state is allowed to stand in for presentation evidence while fallback rendering is already constrained by Gen2 ownership.

SECOND SOURCE-CONFIRMED FINDING
`Fold7PresentationLease` is instantiated inside each `DisplayMirrorHost`. Its `hostEpoch` and `attemptSequence` both start from zero in each new host object. Every new host calls `openHost()`, yielding hostEpoch=1. For the FROZEN_VIEW path, a replacement host can consume the same exact-cycle contentLeaseId. The tuple:
  serviceEpoch + closeCycleId + contentLeaseId + hostEpoch + attemptSequence + renderPath
can therefore be identical across two distinct host objects after remap/recreation.

CURRENT stale callbacks are still locally fenced because each callback closes over its own host-local lease object and detach invalidates that local owner. This finding is NOT evidence of current cross-host state corruption. It means the current identity is host-local rather than service-global and is unsafe as a future cross-host visible-ownership token or globally unique causal join key without adding a stable external host lease identity.

PLATFORM EVIDENCE DISTINCTION
- ViewTreeObserver.registerFrameCommitCallback: frame rendered and submitted to swap chain; Android explicitly says the frame may not yet be visible.
- SurfaceControl.Transaction.addTransactionCommittedListener: transaction applied/ready to be presented; not proof of physical presentation.
- SurfaceControl.Transaction.addTransactionCompletedListener (API 35): invoked when the transaction is presented.
- A valid presentFence signal gives stronger timing evidence (an actual presentation timestamp); absence of a usable fence must not erase the fact that TransactionCompleted itself is presentation evidence.

DOMINANT LIMITATION
There is no service-stable exact presentation owner connecting:
  visual demand -> exact visual attempt -> exact host -> exact content -> render submission -> terminal presented evidence.

GEN3 DIRECTION
Introduce a service-stable PresentationOwner beneath the display-rd CoverVisualLease. Controller COVER_VISUAL becomes demand, not proof. A visual attempt becomes PRESENTED only when the exact current presentation attempt receives render-path-appropriate presentation evidence. Host replacement/retry/content replacement creates a new exact presentation identity. Old callbacks remain observable but inert.

MODEL VALIDATION
Pure Kotlin model compiled and passed 13/13 deterministic/adversarial tests, including a fixed-seed 100,000-event stream.

CONFIDENCE
- HIGH: source-level requested-vs-presented gap.
- HIGH: host-local identity collision across newly constructed frozen hosts.
- HIGH: Android evidence-strength distinctions described above.
- MODEL-LEVEL: proposed service-stable owner invariants.
- DEVICE VALIDATION REQUIRED: exact Fold7 callback timing, frozen-view draw-synchronized presentation proof, fallback behavior, and user-visible transition quality.

5. DOMINANT FAILURE MODE
==================================================

CURRENT has REQUESTED STATE masquerading as PRESENTED STATE.

The problematic chain is:
  controller enters COVER_VISUAL
  -> ShowMirror issued
  -> mirrorRequested=true
  -> visualMirrorActive=true
  -> service may suppress/avoid other rendering work
  -> host/session/content/presentation can still be absent or fail later

A robust architecture must never let “we asked for a visual” become “the user is seeing that visual.”

This is especially important during:
- first session open;
- display topology churn;
- logical-ID remap;
- host construction/attach failure;
- frozen-frame rejection;
- live mirror creation failure;
- geometry transaction failure;
- close->open reversal while callbacks are queued;
- content replacement within the same close cycle;
- service/privilege epoch changes.

6. GEN3 PRESENTATION OWNER DESIGN
==================================================

6.1 Placement

Preferred location:
  Fold7Gen2Kernel (or the Gen3 successor composition root)

Reason:
- lifetime is service-stable rather than DisplayMirrorHost-stable;
- it can correlate cycle, visual owner, host, content, and callback state;
- it survives host replacement while invalidating old attempts deterministically;
- it remains independent from Android side effects.

Do not make DisplayMirrorHost the service-level presentation authority.

6.2 Identity

Conceptual immutable Identity:

PresentationIdentity(
  serviceEpoch,
  closeCycleId,
  transitionGeneration,
  visualAttemptId,
  hostLeaseId,
  contentLeaseId,
  presentationAttemptSequence,
  renderPath
)

Identity rules:
- serviceEpoch comes from service/Gen3 kernel lifetime.
- closeCycleId comes from the exact active close cycle where applicable.
- transitionGeneration is captured at visual demand/attempt creation, not looked up later in callbacks.
- visualAttemptId comes from display-rd CoverVisualLease (or the exact accepted visual owner equivalent).
- hostLeaseId is allocated monotonically by the service-stable owner/coordinator BEFORE DisplayMirrorHost construction.
- contentLeaseId is the exact frozen-frame lease or live mirror content lease.
- presentationAttemptSequence is service-stable/owner-stable and never restarts with a new host object.
- renderPath is explicit: FROZEN_VIEW, LIVE_MIRROR, and any future compositor path.

Do not use Android logical display ID as physical identity.
Do not reconstruct identity from “current” mutable state inside callbacks.

6.3 State

Recommended state model:
- IDLE
- REQUESTED
- HOST_READY
- SUBMITTED
- PRESENTED
- FAILED
- INVALIDATED

State semantics:
REQUESTED: visual owner demanded this exact attempt; no physical presentation claim.
HOST_READY: exact host exists and can accept/bind content; no physical presentation claim.
SUBMITTED: content/frame/transaction has entered the rendering/presentation pipeline; no physical presentation claim.
PRESENTED: terminal evidence proves the exact current attempt was presented according to its render-path contract.
FAILED: current attempt could not proceed; visual owner must decide fallback/retry.
INVALIDATED: reversal/remap/new attempt/authority loss/service lifecycle made the attempt stale.

6.4 Evidence strength

Recommended explicit evidence enum:
- NONE
- DRAWN
- FRAME_COMMITTED
- TRANSACTION_COMMITTED
- PRESENTED_CALLBACK
- PRESENT_FENCE

Rules:
- DRAWN is not presented.
- FRAME_COMMITTED is not presented.
- TRANSACTION_COMMITTED is not presented.
- PRESENTED_CALLBACK can assert PRESENTED when the platform contract says callback occurs on presentation.
- PRESENT_FENCE is PRESENTED plus stronger actual presentation timestamp quality.
- Callback arrival timestamp and presentFence.signalTime are separate values.

6.5 LIVE_MIRROR terminal evidence

On API 35+:
- transaction committed callback -> SUBMITTED/TRANSACTION_COMMITTED only.
- transaction completed callback -> PRESENTED/PRESENTED_CALLBACK.
- if presentFence is valid/signaled -> evidence=PRESENT_FENCE and store exact signal time.
- if presentFence is invalid/empty but completed callback fired -> remain PRESENTED/PRESENTED_CALLBACK; do not incorrectly downgrade to “not presented.”

Current code only calls Fold7PresentationLease.onPresented when a valid fence signal is obtained. For ownership semantics, this is too strict because the API completed callback itself is documented as presentation completion. Keep fence validity as timestamp quality, not as the binary visibility test.

6.6 FROZEN_VIEW terminal evidence

Current frame-commit callback is insufficient to assert PRESENTED.

Recommended Gen3 direction:
- preserve frame-commit as SUBMITTED/FRAME_COMMITTED evidence;
- add a real presentation primitive for the frozen View path.

Best candidate to prototype:
- create a tiny transaction tied to the host root SurfaceControl;
- schedule it on the same draw using the existing draw-synchronized transaction mechanism;
- register API35 TransactionCompletedListener;
- capture exact PresentationIdentity before registration;
- completion may assert PRESENTED_CALLBACK; valid present fence upgrades timing evidence.

This must be validated on Fold7. The R&D model proves the ownership semantics, not that a specific no-op/root transaction is guaranteed to track the desired View buffer on Samsung. If that coupling cannot be proven, keep FROZEN_VIEW as PRESENTATION_UNCONFIRMED and let the visual owner choose an explicit degraded policy rather than falsely asserting visibility.

6.7 Host remap/recreation

On every new DisplayMirrorHost construction:
- allocate a new service-stable hostLeaseId first;
- invalidate any current attempt bound to the replaced host;
- construct the new host with hostLeaseId and the shared PresentationOwner;
- rebinding the same visual/content demand creates a new presentation attempt identity;
- old host callbacks may be logged as stale but must not mutate current ownership.

6.8 Content/path replacement

Changing any of:
- frozen contentLeaseId;
- live mirror lease/content identity;
- renderPath;
- visualAttemptId;
creates a new presentation attempt.

A newer attempt must invalidate the older one before callbacks can race.

6.9 Reversal/authority loss/service restart

Before releasing route/host on reversal or authority loss:
- invalidate current exact presentation attempt synchronously in the service-stable owner;
- then detach/release Android resources.

This ordering guarantees late callback inertness.

Service restart changes serviceEpoch, so old callbacks cannot match even if numeric cycle/content counters restart.

==================================================
7. RELATIONSHIP TO DISPLAY-RD COVER VISUAL LEASE
==================================================

DO NOT merge visual intent and presentation evidence into one owner.

Accepted layering should be:

cover authority
  -> cover readiness
  -> content provenance
  -> CoverVisualLease / exact visual intent + compositor ownership
  -> PresentationOwner / exact host-content attempt + presented evidence

CoverVisualLease answers:
  “Which exact visual attempt is authorized and demanded?”

PresentationOwner answers:
  “Has that exact visual attempt actually been presented on its current exact host/content path?”

This work therefore strengthens, rather than competes with, display-rd’s proposal.

PresentationIdentity.visualAttemptId should be copied from the accepted visual lease. Never discover “current visual” at callback time.

==================================================

Do NOT implement P1.2 as only:
  rename visualMirrorActive -> visualMirrorPresented
or
  change FoldOverlayService to evaluate PanelEngine when not presented.

That is insufficient and may create renderer contention.

CURRENT Fold7CoverRenderPolicy grants privileged Gen2 blanket cover ownership, and PanelEngine is deliberately suppressed under that ownership. Recommended integration ordering:
1. P0.2 exact CoverVisualLease/compositor owns visual fallback/degradation.
2. P1.2 PresentationOwner reports pending/presented/failed beneath that owner.
3. Visual owner chooses retry, static degraded presentation, or native handoff explicitly.
4. Never implicitly revive legacy autonomous cover rendering merely because presentation is pending.

The PresentationOwner foundation can be coded/tested independently, but behavior changes should be reconciled with P0.2.

11. REJECTED / NEGATIVE DIRECTIONS
==================================================

REJECTED: treat mirrorRequested/COVER_VISUAL as proof of visibility.
Reason: source directly demonstrates pre-host/failure windows.

REJECTED: treat View frame commit as physical presentation.
Reason: Android explicitly says frame may not yet be visible.

REJECTED: treat transaction committed callback as physical presentation.
Reason: committed means applied/ready to present, not presented.

Reason: API contract says completed listener is invoked when presented; fence availability should affect timestamp quality, not erase presentation evidence.

Reason: remap/retry/reversal callbacks can cross.

REJECTED: keep hostEpoch local to each DisplayMirrorHost if identity is used outside that host.

Reason: would contaminate rendering latency and risk jank/deadlock.

REJECTED: change 174-degree prewarm / 135-degree visible threshold to hide presentation failures.

REJECTED: reactivate autonomous legacy cover PanelEngine as an implicit fallback.

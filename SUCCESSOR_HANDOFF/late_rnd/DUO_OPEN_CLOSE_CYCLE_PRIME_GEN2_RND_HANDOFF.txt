1. EXECUTIVE SUMMARY
======================================================================

SUBSYSTEM
Close-cycle continuity-frame priming ownership and stale-capture fencing.

WHY SELECTED
Primary had already identified P1.1: the "prime once per close cycle" guard is
owned by mutable PanelEngine instances even though the close cycle itself is a
service-stable Fold7CycleEnvelope identity. Prior Fold7 field evidence carried
by primary observed a second continuity prime near ~5 degrees during a display/
engine remap. No active live Agent Bus workstream was owning this redesign when
this workstream was claimed.

DOMINANT LIMITATION
Current main places `primedContinuityCycleId` inside each PanelEngine. A Samsung
logical-display/engine replacement creates a new PanelEngine whose guard starts
at -1, so the same exact close cycle can reserve a second prime. The first
engine's prime coroutine runs in the service MainScope and is not cancelled by
PanelEngine.destroy(), so both old and replacement attempts can remain in flight.

A second source-level defect compounds this: Fold7ContinuityFrameStore assigns
monotonic captureSequence values at beginCapture(), but publish() rejects an old
ticket only relative to the newest already-PUBLISHED frame. It does not reject
an older attempt merely because a newer attempt has already STARTED. Therefore:

  capture #1 starts
  engine remaps
  capture #2 starts
  capture #1 completes first
  -> current publish() can accept #1 because latest == null

If #2 then fails, #1 can remain current even though beginCapture(#2) explicitly
said the newer attempt superseded the previous frame immediately.

GEN2 DIRECTION
Move prime-attempt ownership into a service-stable Gen2 kernel/cycle owner. Give
each explicit prime/retry an immutable attempt token:

  serviceEpoch + closeCycleId + attemptSequence

Engine/host/display identity is attribution/source identity only; it must not be
the once-per-cycle authority. An engine replacement cannot obtain a second
attempt unless the current exact attempt was explicitly abandoned/failed and a
retry was authorized. In parallel, Fold7ContinuityFrameStore must track the
newest STARTED capture sequence and accept publish only from that exact newest
started attempt. This creates two independent stale-result fences.

STRONGEST EVIDENCE
1. CURRENT source reconstruction at exact main SHA confirms the mutable-engine
   guard, service-scope prime coroutine, remap-driven engine recreation, and
   frame-store start/publish ordering gap.
2. Reduced source-faithful baseline model reproduces both defects.
3. Proposed ownership model passes 14/14 deterministic/adversarial tests plus a
   deterministic 100,000-event stale/duplicate/remap property stream.
4. Primary's prior Fold7 evidence records the real second-prime symptom near
   ~5 degrees during remap.

CONFIDENCE
HIGH for the source-level ownership/race defects and the reduced-model
invariants. MEDIUM for exact Android integration shape until primary implements
and runs full Gradle tests. Device behavior remains field-validation dependent.

LARGEST UNKNOWN
How Samsung's real Fold7 topology-remap timing overlaps Shizuku screenshot
completion under fast transitions, and whether source loss needs an immediate
retry or a short bounded grace interval for best real-device latency. The owner
model supports either policy without weakening exactness.

8. GENERATION-2 DESIGN
======================================================================

RESPONSIBILITIES

1. Fold7CycleEnvelope
Owns stable serviceEpoch + closeCycleId. Unchanged.

2. New service-stable prime owner
Recommended name: Fold7ContinuityPrimeOwner (exact name primary may choose).
Recommended owner: Fold7Gen2Kernel.
Owns authorization/state for one prime lifecycle per current close cycle.

3. Capture source / PanelEngine
Provides a currently valid inner physical source capable of executing the
screenshot. It does NOT own whether a prime may exist.

4. Fold7ContinuityFrameStore
Owns content ticket/lease ordering and must independently reject an older ticket
once any newer capture attempt has started.

STATE MODEL

NO_CYCLE
  no active close cycle

ELIGIBLE
  current close cycle exists; no attempt yet

IN_FLIGHT(attemptSequence, sourceEpoch)
  one exact attempt reserved

RETRYABLE(previousAttemptSequence, reason)
  exact current attempt failed/was abandoned; retry requires explicit begin

READY(attemptSequence, contentLeaseId)
  exact prime published; no duplicate prime in same cycle

FALLBACK_ALLOWED(reason)
  prime path intentionally yielded; generic continuity capture may proceed

IDENTITY
PrimeAttempt:
- serviceEpoch
- closeCycleId
- attemptSequence
- optional sourceEpoch/hostEpoch for attribution and exact callback source

Do NOT use logical display ID as persistent authority. A logical ID can be
recorded for diagnostics but must not be the cycle identity.

LIFECYCLE
- beginClose -> owner.beginCycle(cycle) => ELIGIBLE.
- service wants prime -> owner.tryBegin(cycle,currentSourceEpoch) atomically
  returns exact token or null.
- only after token reservation may capture start.
- source remap alone does NOT grant replacement source a token.
- source loss can explicitly abandon exact in-flight token -> RETRYABLE.
- retry increments attemptSequence and reserves a new exact token.
- successful current token publish -> READY.
- reversal/native takeover/service stop -> invalidate cycle; old callbacks inert.
- new close cycle -> fresh identity, independent sequence.

CONCURRENCY / CANCELLATION
- Completion first checks prime owner token exactness.
- FrameStore publish then checks capture ticket is newest-started for the cycle.
- Both must pass. One fence is not a substitute for the other.
- A destroyed source cannot mutate the owner merely because its coroutine
  returns. It can only complete/fail/abandon with the exact token.
- If source destruction can be synchronously observed, explicit abandon makes
  retry immediate. Otherwise stale callback is harmless and a timeout can move
  current token to RETRYABLE.

FRAME-STORE HARDENING
Add per-cycle newestStartedCaptureSequence (or exact active ticket identity).
On beginCapture:
- increment sequence;
- set newestStartedCaptureSequence to ticket sequence;
- clear latest.
On publish:
- require ticket.serviceEpoch/closeCycleId current;
- require ticket.captureSequence == newestStartedCaptureSequence;
- retain existing timestamp/provenance checks.
This makes "newer attempt supersedes older immediately" true in code, not only
in comment.

RECOVERY
- Failed current attempt -> RETRYABLE.
- Primary can choose bounded retry count/time policy separately.
- Explicit FALLBACK_ALLOWED permits generic current-cycle capture without
  accidentally racing the prime.
- Never resurrect a pre-supersession frame after a failed newer attempt.

DEGRADATION
- If no valid inner source or repeated capture failure, mark explicit fallback
  reason and allow the existing safe downstream/native path.
- No stale prior-cycle substitution.

INVARIANTS
I1. At most one authoritative prime attempt is IN_FLIGHT per exact close cycle.
I2. Engine/display remap alone never creates a new prime attempt.
I3. Every retry has strictly greater attemptSequence.
I4. Only exact current attempt token may transition owner to READY/RETRYABLE.
I5. Once a newer capture starts, older capture tickets can never publish.
I6. Old service/cycle callbacks are inert.
I7. READY blocks duplicate same-cycle prime.
I8. Generic continuity capture requires explicit owner policy, not an engine-
    local boolean reset.
I9. Logical display ID is source metadata, not persistent physical identity.
I10. No changes to physical panel power, task migration, or hinge thresholds.

13. REGRESSION RISKS
======================================================================

CORRECTNESS
- Overly strict store fencing could reject a legitimate independent capture path
  if multiple capture classes share one sequence without explicit policy.
  Mitigation: make all exact-cycle frame attempts use a deliberate unified
  arbitration contract or distinguish capture purpose while maintaining a
  single newest-authoritative sequence.

LATENCY
- Explicitly serializing prime attempts could delay fallback if timeout/retry
  policy is too conservative. Measure before choosing timeout.

POWER
- Expected improvement from eliminating duplicate screenshots during remap, but
  no device power measurement exists.

SAMSUNG INTERFERENCE
- Remap may happen while old capture remains usable. Architecture rejects stale
  authority safely but retry timing must be measured on Fold7.

LIFECYCLE
- Must invalidate owner before stale service/source callbacks can act during
  reversal/service destruction.

RACES
- Owner exact-token check and frame-store newest-started check must both exist.
- Do not rely only on coroutine cancellation; Binder/shell work may complete
  after cancellation intent.

RENDERING
- Frame-store hardening changes which frame survives races; fallback visuals may
  show no exact frozen frame rather than an older superseded one. This is
  intentional correctness but must degrade cleanly.

RESTART BEHAVIOR
- serviceEpoch must invalidate prior attempt identity and store state.
